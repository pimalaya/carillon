# Generate a first account from an email address

carillon was the only Pimalaya CLI meeting a newcomer with "copy config.sample.toml and delete the rest". It now meets them the way himalaya, comodoro and ortie do.

## What landed

`src/wizard/` holds the himalaya wizard system, adapted to a tool that watches rather than reads. `carillon configure` (alias `wizard`) runs it, and a bare `carillon`, or any command finding no configuration, offers it with a welcome naming the file that is missing. A non-interactive caller, no terminal or `--json`, is never prompted: it fails naming the file and the command that would create it. `Config::load` stopped bailing on a missing file and became the plain loader; the offer lives in `cli::load_config`, which is where the printer and the terminal test are.

One prompt takes an email address, a bare domain, a `scheme://` URL or a folder path. `wizard/search.rs` runs io-pim-discovery over the four services carillon can watch (IMAP, JMAP, CalDAV, CardDAV) and folds each service's advertised methods into the capabilities that drive the auth prompt; a folder short-circuits to Maildir. The chosen service prompts its SASL mechanism or HTTP scheme among those advertised, then its credential through pimalaya-cli's keyring and OAuth-broker picker, so what lands in the file is a read command rather than a secret.

The connection test is where the wizard earns its keep, because it is also what completes the account. IMAP opens the session and reads the capabilities back: no IDLE means an explicit `imap.watch.poll.interval`, and IDLE means nothing at all is written, an unset `watch` already being IDLE. JMAP does the same with the session's event-source URL. DAV has more to complete: discovery names a context root, which is not something to watch, so the wizard walks the principal and the home-set and offers the calendars or addressbooks that account holds; the chosen one becomes `caldav.calendar` or `carddav.addressbook` as an absolute path under the authority that answered, and the calendar's `supported-calendar-component-set` decides whether the account gets event hooks, task hooks or both, since a hook naming a component the calendar does not hold is refused when the watch starts.

A generated account carries one notify hook on arrival. A watch with no hook watches and does nothing, and the wizard's job is an account that works when it is saved.

The account is then a file to create, a block to append or a document on stdout, with the same rules as the other tools: a free name, the default claimed only when no other account does, and a plain text append that leaves comments and formatting untouched. Rendering it forced two things in `config.rs`: `skip_serializing_if` on the fields carrying a default, so a generated document holds only what was configured, and an `AccountConfig::render` that reorders the flattened dotted keys, since alphabetical order buries `imap.server` under the credentials that authenticate against it. A backend group now reads the way it is explained: the collection it watches, the server, the credential, then everything the account only adjusts.

`--help` gained the shared `footer!()`, the bug tracker and the sponsoring page, which carillon was also alone in missing.

io-pim-discovery is a dependency of the three network backends rather than of the crate, so a Maildir-only build pulls no DNS or HTTP discovery stack and compiles the search half out.

## Verification

Build, clippy, fmt and the tests green on every feature combination (none, imap, jmap, maildir, dav, and all four); 39 tests, 12 of them new: the render order and its round-trip through the parser, the account-name suffixing, the append that keeps the existing account, the discovery scheme filter, the mechanism menu narrowing, the DAV collection path and component-keyed hooks, the folder-versus-endpoint split. The non-interactive paths were run against a missing configuration: the bare invocation falls back to the help, `check` fails naming the file, `configure` refuses to run without a terminal.

No live provider has been through the wizard yet; that is the open task on the change, alongside the same one for the watches themselves.

## Not done

Gmail and Microsoft Graph short-circuits, since carillon has no proprietary backend: a Google or Microsoft account is configured over IMAP or DAV like any other. Hooks beyond the arrival one, flag filters and notification templates are not prompted either, prompting for those being a worse text editor than the one the user already has.

## Follow-up: the server decides the mechanism menu, not discovery

Reviewed on the day it landed: the wizard offered SCRAM-SHA-256 first for a Gmail address, and Gmail has never implemented SCRAM.

The cause was a half-ported flow. himalaya's IMAP wizard offers what a live `CAPABILITY` probe read, and keeps a list keyed on discovery only as the fallback; carillon had kept the fallback and dropped the probe. That list is a guess by construction: discovery reports a provider's *policy*, that a password and an OAuth grant are accepted, and never which mechanism carries the password. Ordered most-preferred-first, it therefore leads with SCRAM-SHA-256 for every provider whose policy names a password, Gmail included.

`wizard/imap.rs` now opens an unauthenticated session first, purely to read the capabilities, and offers `available_auth_mechanisms` (most preferred first, LOGIN last, and filtered to what `imap.sasl` has a table for). The probe costs one extra connection, which is the same price himalaya pays. A probe that fails is logged and falls back to the discovered list rather than stopping, so an unreachable or silent server narrows nothing instead of emptying the menu.

The other two protocols keep their discovered lists: an HTTP service answers with `WWW-Authenticate`, which discovery already probes and folds into the capabilities it reports, so there is no second word to ask for.
